# Architecture

One FastAPI process integrates seven service areas. SQLAlchemy 2.x declarative models define the domain schema; SQLite is the local persistence layer. Schema creation is automatic on startup and via CLI. Spatial matching is disabled until sourced boundary data is supplied.

Ingestion validates provenance. News processing redacts phone/email patterns and offers reviewable candidate similarity scoring. Locality resolution requires exact gazetteer evidence; no gazetteer is bundled. Trend queries keep official and article-derived series separate. The geocoding API returns selectable OpenStreetMap Nominatim place suggestions; chosen display names and exact coordinates are preserved into route requests. The route API requests actual road geometry and alternatives through OSRM, defaulting to its public demonstration endpoint unless `NAVIRA_OSRM_BASE_URL` is configured. `NAVIRA_MAX_ROUTE_ALTERNATIVES` controls the total returned-route limit (default 3, range 1–5); OSRM's numeric `alternatives` option requests up to one fewer alternate in addition to the fastest route (`false` when the maximum is 1). Invalid geometries are discarded; routes with at least 85% of both sampled paths within 80 m are treated as substantially overlapping and deduplicated. A one-route response remains one route; no synthetic routing fallback is used.

Only explicitly verified, dated, precisely geocoded newspaper records are matched to route segments using the configurable proximity and age window. Each returned route receives its own match count, matched sources, and evidence-gated assessment. NCRB registered-case statistics remain separate city-level historical context. Current Open-Meteo data can be enabled separately; it uses the resolved route-origin coordinates only and is included only when its timestamp is at most three hours old. TomTom traffic uses the existing provider adapter and is requested independently per distinct route with bounded concurrency; provider errors or missing keys do not remove valid road routes. Community reports are unverified and expiry-filtered. Emergency resources expose a dial action without claiming calls were placed.

The selected route's infrastructure card calls `POST /api/v1/routes/infrastructure` with its GeoJSON coordinates and a selectable 50–500 m corridor. The service queries live OpenStreetMap/Overpass `highway=street_lamp` nodes and pedestrian-tagged ways (`footway`, `path`, `pedestrian`, `steps`), filters returned geometry against the selected route, and reports the OSM base timestamp and query retrieval time. Counts mean mapped features only. OSM `lit` tags describe map records, not operating streetlights; working condition remains unverified and night visibility remains unassessed. Delhi PWD, MCD, and NDMC pages are linked, but no route-level government inspection or complaint feed is configured, so those records stay unavailable. Infrastructure evidence is not consumed by or used to alter the safety assessment. The route-corridor sampling limit and OSM completeness are disclosed; an empty result is not interpreted as absence of infrastructure.

## Route evidence methodology

The route review considers four classes of input: review-verified, dated, source-linked, precisely geocoded newspaper reports matched to route geometry; historical official incident statistics; current TomTom flow samples; and sourced infrastructure audits such as lighting or pedestrian activity. The first is observational and has no complete incident or route-exposure denominator. The bundled NCRB Delhi City data is metropolitan aggregate context, not route- or locality-level evidence. Traffic describes travel conditions and provider samples, not personal safety. Live OSM map records are displayed as route context, not as an infrastructure audit; no government inspection or route-covering field lighting audit is currently configured.

No probability of harm is computed. NAVIRA can now show a separate **provisional route audit index** when all returned routes meet the review and coverage gate: observations must be no older than 180 days, within 50 m of at least 60% of evenly sampled route points, and cover at least five distinct segments. The index equally averages nine human-audited 0–3 dimensions (lighting, openness, visibility, crowd/activity, security, walk path, public transport, gender diversity, and feeling of safety) and scales that mean to 0–100. These equal weights are a transparent NAVIRA starting policy, not a validated predictor and not the proprietary Safetipin score. The app orders routes by the index only if every option clears the same gate. Otherwise it labels the fastest provider option as a navigation fallback and says that no safest route can be identified. Verified newspaper matches, citywide NCRB totals, traffic, weather, and mapped OSM features remain separate context; none is treated as an incident rate or silently added to the index. Empty, missing, stale, or unreviewed data never increases a route score. The current repository has no licensed street-audit dataset imported, so the live site will continue to show the fallback until reviewed data is supplied.

Initialize with python -m backend.app.cli init-db from the repository root. No migration framework is included; back up the SQLite database before future schema changes.


## ML workflow

The model-fitting code is in the separate repository-level `ml/` package. The backend adapter applies redaction, persists model artifacts and run metadata, and exposes prediction/training operations. The TF-IDF plus LogisticRegression pipeline trains only from explicit human labels (0/1). It uses a deterministic source-group holdout when at least four source groups and both classes remain represented; otherwise it reports a seeded stratified fallback. It reports precision, recall, F1, confusion matrix, class balance, split type, and dataset fingerprint. Small/imbalanced data skips honestly. It does not predict crime risk.
